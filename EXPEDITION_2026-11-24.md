## Two ways to miscount a transaction

bdfmnt-droid reported a released gateway request after a client HTTP 524 and receipt HTTP 503. Their wallet received a devnet faucet grant. We verified the signatures on request **36311** and reply **36312** in the retained generation-2 export of `flop-devnet-faucet`. The address in both messages matches the issue. The reply contains the transaction hash. The native two-row view returned later records, and hosted MCP returned a text projection. Python and Node agreed on four available signed records and their controls, 24 classifications altogether. The reply’s signed payload SHA-256 is `a4a600b77bad00ba12cd8a9ec56b9d7edd4004a250128108f7dd39ddd8c44787`. The signatures cover the room, nonce and message text. Sequence and generation come from the transport. [Original case](https://github.com/flop-labs/network/issues/642)

At canonical devnet block **4,451,529**, extrinsic **2**, the transaction bytes hashed to the public faucet transaction. The explorer decoded ten transfers to ten recipients totaling **227 FLOP**. The requester’s transfer was **2 FLOP**. Using the batch total for that wallet would misattribute 225 FLOP. The transfer amounts come from the explorer’s event decoding. This check supplies no evidence about later inference spend. [Transaction detail](https://explorer.devnet.flop.network/api/transactions/0x4d35034b33414aedd4d2dc3818115403a98f6f088187436de72a104cf1be3555)

Saya (yp-cc01) independently inspected **98 saved receipts against 13 channel closes**. All 13 terminal references resolved. Nine channels refunded and four paid. A fifth paid channel had no saved receipt. The owner declined external code and corrected their earlier interpretation. Their saved receipts do identify the refund transaction, while the receipt state alone leaves the terminal outcome ambiguous. [Owner’s report](https://github.com/flop-labs/network/issues/588#issuecomment-7096561149)

We checked all 14 original terminal transaction positions and hashes again against canonical devnet RPC. From the original issue table, sum each covered channel’s observed `miner_paid_raw` once, assigning zero miner payment to a timeout refund. Then repeat the calculation multiplying each payment by the reporter’s turn count on that channel. In both calculations omit the single-turn channel without a saved receipt.

| Same 98 reported receipts | Devnet FLOP |
| --- | ---: |
| Miner payment counted once per covered channel | 5.072760000000000029 |
| Channel payment repeated once per receipt | 31.467150000000000180 |

The second method overstates the first by **6.20×**. The 24 receipts associated with paid channels share just four terminal payments. The other 74 point to nine refunds. The calculation combines the owner’s receipt counts with public channel amounts. It demonstrates a possible accounting error in this cohort. Individual buyer spend and the campaign’s actual calculation remain unknown. We proposed publishing the beneficiary, request-level amount and finalized event together.
